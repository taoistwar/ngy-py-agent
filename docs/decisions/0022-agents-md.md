# ADR 0022: AGENTS.md —— 工作区的项目指令进入系统提示词

- 状态：已接受（Accepted）
- 日期：2026-11-16
- 相关：`agent/agents_md.py`、`agent/agent_loop/loop.py`、`admin_api.py`、`task_runtime.py`、`app_state.py`、`task_store.py`、`web-admin/src/components/admin/SettingsPanels.jsx`、`test/agents_md_test.py`、`test/agents_md_config_test.py`、`test/agent_loop_agents_md_test.py`
- 前置：[ADR 0007](0007-default-workspace.md)（未绑定会话的基目录）

## 背景

在此之前，agent 的行为完全由**配置**决定：模式/智能体的系统提示词、内置技能、可用工具集。它对**项目本身**一无所知——用什么命令跑测试、提交前必须跑哪几个检查、代码风格是什么。用户只能在每条任务里重复交代一遍，而重复交代是稳定的失真来源（漏一条，模型就少一条约束）。

[agents.md](https://agents.md/) 是这个问题上的开放格式，规则只有三条：

1. `AGENTS.md` 放在仓库根目录，是纯 Markdown，没有 schema、没有必填字段；
2. monorepo 可以在每个包内再放一份，**离被编辑文件最近的那份优先**；
3. 用户在对话里的显式要求覆盖这一切。

这里最容易混淆的是**两份同名文件**：

- 本仓库根目录的 `AGENTS.md` 是给**改这个仓库**的编码助手看的开发约定（怎么拆文件、怎么提交）；
- 运行时 agent 要遵守的是**用户绑定的工作区**里那一份：任务操作的是那个目录，构建/测试命令、代码风格都属于它。

两者受众不同，内容还会互相矛盾——本仓库的"改完自动提交"对用户的上游项目毫无意义。在此之前，任务消息里只有 `## Working directory` 这一段环境信息，工作区的规则完全传不进去。

## 决策

### D1. 只读已绑定的工作区

`base_dir` 为空时不读任何文件。未绑定会话的相对路径基目录是 `data/default_workspace`（ADR 0007），那是草稿区而不是项目；把草稿区里的文件当成项目规则，只会让"规则从哪来"变成一个查不清的问题。

同一条规则也排除掉一个更诱人的错误：**进程自己所在的仓库不是工作区**。本仓库的 `AGENTS.md` 是写给维护者的开发约定；只有当调用方显式把某个目录作为 `base_dir` 绑定时，那个目录里的文件才会被读。

### D2. 根文件内联，嵌套文件只建索引

根 `AGENTS.md` 全文进入系统提示词；子目录的 `AGENTS.md` 只列成路径清单，并明确告诉模型"改到那个目录之前先 `read_file` 读它，最近的那份优先"。

全量内联不可取：OpenAI 主仓库一度有 88 个 `AGENTS.md`，把没被碰到的包的规则也塞进每一轮请求，是在为不会执行的指令付费。而"最近者优先"本来就要求模型知道去哪找——索引是那条规则的最小实现。

索引上限 `NESTED_FILE_LIMIT = 20`，超出的在清单末尾说明条数并指向 `glob`（`**/AGENTS.md`）。

### D3. 名称：`AGENTS.md`，兼容旧名 `AGENT.md`

规范建议的迁移方式是重命名 + 反向符号链接；直接读旧名覆盖那些没做过迁移的仓库。同一目录同时存在两份时只用 `AGENTS.md`，不合并——合并会产生一份谁也没写过的规则。

### D4. 单文件上限 `AGENTS_MD_MAX_BYTES`，默认 32 KiB

系统提示词是每一轮都要重新付费的部分，一个失控的文件不能独自吃掉上下文。取 32 KiB 与 Codex 的项目文档上限一致：足够写清构建、测试、风格与提交规范。截断按 UTF-8 字节做，不切断字符，并在截断处写明"上限多少、剩余部分用 `read_file` 读"。

### D5. 扫描范围：深度 3，跳过依赖与产物目录

`os.walk` 到第三层为止，跳过点目录（`.git`、`.venv`…）与 `node_modules` / `venv` / `dist` / `build` / `target` / `vendor` / `__pycache__`。索引只是目录，但它必须在 88 个文件的仓库上也保持毫秒级，且不能走进依赖树里那些第三方包自带的 `AGENTS.md`。

### D6. 只在 `run_react_loop` 自建消息时注入

- **Web Admin / 库调用**：`run_react_loop` 组装消息时注入（`agent/agent_loop/loop.py`），条件是 `base_dir` 指向一个已绑定的工作区。
- **`initial_messages` 非空时一律不注入**：续跑重建的 transcript 里，系统提示词是上次请求的原样，改写它等于修改模型已经回答过的历史；调用方提供的对话同理，规则由调用方自己决定。

### D7. 位置：`## Working directory` 之后，作为系统提示词最后一块

顺序表达优先级：模式/智能体的通用指令 → 工作目录 → 项目自己的规则。项目规则比 agent 的默认值更具体，放在最后既符合"越靠后越具体"的惯例，也让工作目录这段短事实不被长文挤到前面。

### D8. 任务日志留一条 `Loaded AGENTS.md`

只记文件名、字符数、是否截断、嵌套索引，**不记正文**（正文已经在那条 `initial_messages` 快照里）。一条"这次任务的规则来自哪里"的记录，是把"模型为什么这么做"从猜测变成核对的最小代价。

### D9. 开关与上限：全局配置（数据库优先，环境变量兜底）

开关与上限是**一项全局配置**：Web Admin「全局配置 → AGENTS.md 项目指令」写入 `settings` 表的 `agents_md_config`，启动时 `admin_api.load_startup_config` 解析进 `app_state`，任务在 `task_runtime.resolve_agents_md_settings()` 读取并交给循环——**下一次任务生效，不需要重启**。环境变量 `AGENTS_MD_ENABLED` / `AGENTS_MD_MAX_BYTES` 只提供默认值，库值优先。

为什么放在管理页：这两个值决定的是**项目规则进不进上下文**，用户改完工作区的 `AGENTS.md` 需要它立刻生效；让人去改 `.env` 再重启，是把配置问题变成运维问题。

允许范围 1024–1048576 字节：请求超界由 API 拒绝（422），库里已有的超界值在加载时夹紧。

两个字段存在**一行 JSON** 而不是两个键，是为了让"当前来源"只有一个答案：两个键就可能一半来自数据库、一半来自环境变量，而面板只能显示一个来源。

## 后果

- 根 `AGENTS.md` 变大 = 每轮成本上升。上限与截断提示兜底，但"把整个 wiki 塞进 AGENTS.md"仍然是一个会变贵的选择。
- 嵌套文件的正文要模型自己 `read_file`，所以 `plan` 模式（无工具）只能看到索引。这没有新增问题：该模式的契约本来就是"不执行、不看文件"。
- 未绑定工作区的会话读不到 `AGENTS.md`，哪怕进程的 cwd 里有——本仓库自己那份就是例子。要规则就绑工作区。
- 文件里的规则高于 agent 的默认提示词，因此一个写着"提交前必须跑测试"的 `AGENTS.md` 会让 `ask` 模式也去跑命令。这是有意的取舍：项目规则是用户自己写的，模式指令是我们写的；冲突时按上下文判断比按固定优先级硬裁更合理。ADR 不再加一层仲裁。
- 依赖树里伪造的 `AGENTS.md` 不会被扫描到，但模型仍可以用 `read_file` 读到它——扫描只决定"自动进入提示词的内容"，不构成访问控制。
- 改开关或上限不需要重启：API 写库并更新 `app_state`，**下一次任务**读新值；已经在跑的任务沿用启动时读到的设置。

## 备选方案（未采用）

- **把本仓库的 `AGENTS.md` 当成运行时规则**：那是维护本仓库的约定，注入只会让运行时 agent 去执行与用户任务无关、甚至与用户项目相反的规则（D1）。
- **全量内联所有嵌套文件**：简单，但把没被碰到的包也算进每一轮上下文（D2）。
- **按最近编辑的文件动态注入**：最贴近"最近者优先"，但要在工具结果之后插入一条新的 system/user 消息，Anthropic 侧还要处理与 `tool_result` 的配对，改动面与收益不成比例。留作后续。
- **启动时缓存内容**：`AGENTS.md` 通常稳定，但单次读取只有几十 KB，缓存换来的是"改文件不生效"的困惑。
- **只认根目录一份**：monorepo 是规范明确支持的主场景（D2、D5）。
- **把规则做成工具返回值**（例如一个 `read_agents_md` 工具）：模型必须先想到调用它，而"不知道有规则"正是当前的问题。
