# ADR 0004: `write_file` 工具的设计

- 状态：已接受（Accepted）
- 日期：2026-09-20
- 相关：`agent/tools/file_write_tool.py`、`agent/tools/read_ledger.py`、`agent/tools/file_bytes.py`、`agent/tools/file_patch.py`
- 前置：[ADR 0002](0002-file-encoding.md)、[ADR 0003](0003-edit-write-and-patch.md)

## 背景

`edit_file` 要求 `old_string` 已存在，所以 Agent 只能改、不能建。"在这个项目里加一个模块"这类任务因此无法完成。本 ADR 记录补上 `write_file`（整体写入）时的取舍。

## 决策

### D1. 只做整体写入，不做追加

`content` 就是文件的全部内容，工具没有 `mode` 参数，也不做追加。

理由：覆盖与追加**没有共同的安全默认值**——本该追加却覆盖会截断文件，本该覆盖却追加会污染文件——所以把两者做成同一个工具，等于把风险交给"模型这次是否选对"，而且选错的代价是无界的。分开之后每个工具的契约都是单一的。追加的做法见文末「追加（待定）」。

### D2. 覆盖已存在文件必须先满足"读过 + 没变"，且这个前置是可强制的

工具不能验证模型是否**理解**了文件，但能验证两件客观事实：

1. 本 run 内对这个文件有过一次**完整读取**（从第 1 行、不带 `limit`），由 `ReadLedger` 记录；
2. 磁盘上的字节仍是那次读取时的字节（`st_mtime_ns` + `st_size` 一致）。

两者之一不满足就拒绝：没有记录报 `read_required`，记录与现状不符报 `file_changed`。**从没被读过的文件因此不可能被摧毁。**

两个补充规则：

- **部分读取不解锁覆盖**（`limit` 或 `offset > 1`）。模型没见过的内容不许被覆盖。
- **写入成功后账本随文件更新**：本 run 已经知道刚写下去的全文，所以连续写入、以及"读 → 编辑 → 覆盖"都不需要再读一次。`edit_file` 只在写入前的指纹与账本一致时才刷新（否则保留旧记录，让下一次覆盖照样报 `file_changed`）。

作用域：**一个 `ToolRegistry` 一份账本**，而 registry 是每次运行新建的，所以别的任务读过的文件不会让本任务获得覆盖权限。

### D3. 编码语义与另外两个工具完全一致

`encoding` 必填（三个工具的 schema 保持一致）、BOM 优先于该参数、行尾沿用文件已有风格、新建文件用 LF。解码失败报 `decode_failed` 并给出候选编码；替换文本在目标编码下不可表示时报 `unencodable_text`。理由与实测见 [ADR 0002](0002-file-encoding.md)。

### D4. 父目录不存在就报错，并给出真实可用的手段

不自动创建父目录：悄悄造目录比报错更难排查。错误里提示用 `code_interpreter`（`os.makedirs`）——工具集里没有 shell，指向一个不存在的工具只会让模型继续乱试。

### D5. 写入是原子的，并保留原权限

**此处偏离最初的规格**（那份规格写的是"原子性未保证，崩溃可能留下部分写入的文件"）。既然 `edit_file` 已经通过"临时文件 + `os.replace`"做到原子，`write_file` 没有理由退回非原子写入——实现成本为零。新建文件用固定 `0644`（不读 umask：读 umask 需要先设置它，在跑多线程任务的进程里不安全），覆盖时沿用原文件权限。

`os.replace` 会换掉 inode，因此**硬链接不再跟随**（与 ADR 0003 D5 相同，已知并接受）。

### D6. 不检查内容差异

内容与现有内容相同时**仍然执行写入**（规格要求）。但会在 `details.content_changed` 里如实报告，供 UI 与历史判断，而不是让调用方以为一定发生了变化。

### D7. 独立事件类别 `file_write`

不复用 `file_edit`：两者对 UI 的含义不同（整体替换 vs 局部替换），历史里能一眼分开。覆盖时携带 `original_file` 与 `gitDiff`；新建时标 `created: true` 且不带这两个字段（没有"从什么变成什么"可说）。

不输出 `structured_patch`：整文件替换下它不提供任何 `gitDiff` 之外的信息，只会把事件体积翻倍（`original_file` 的体积风险已在 ADR 0001 D2 被接受）。

## 后果

- 模型侧只看到一行摘要（`created` / `replaced`），富记录走事件，沿用 ADR 0001 的双通道契约。
- 超过 `read_file` 上限（256KB）的文件**无法**用 `write_file` 整体重写——因为读不全就永远解锁不了。这被视为正确行为：这种文件本来就不该整体重写，应当用 `edit_file`。
- 新增 `read_ledger`（读账本）这一领域概念：它是"本 run 是否持有整份内容"的记录，不是权限系统。
- 前端需要为新事件类别补 i18n 与标签样式（已补 `category_file_write` 与 `.tag.file_write`）。

## 追加（待定）

"追加"目前**由 `edit_file` 承担**：把 `old_string` 锚定在文件最后一行上即可。实测这比"读全文再覆盖"更安全，而且对大文件同样可行：

```
huge.txt 387 KB（超过 256 KB 读取上限，无法整体读取）
read_file(offset=10999, limit=2)  → 尾部两行
edit_file(old="...最后一行", new="...最后一行 + 新内容")
→ success，396000 → 396009 字节，文件头未改动
```

另外它**在重试下是幂等的**：第二次重试时最后一行已经变了，锚点不再匹配，得到 `no_match` 而不是重复追加。

因此是否**再单独做一个追加工具**尚未决定。倾向不做的理由：追加工具没有"锚点不匹配"这道保护，它对"加到哪个文件"没有任何校验；而"留给未来的 Bash"更糟——`>>` 追加既没有编码一致性，也没有 `file_changed` 复核，也不产生事件记录，等于在安全边界上开一个后门。若将来确有高频追加需求，应当设计成**要求锚点**的幂等工具，而不是裸追加。
