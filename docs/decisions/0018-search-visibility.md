# ADR 0018: 搜索的可见范围（glob 排序、grep 忽略规则）

- 状态：已接受（Accepted）
- 日期：2026-10-27
- 相关：`agent/tools/file_walk.py`、`agent/tools/glob_pattern.py`、`agent/tools/glob/search.py`、`agent/tools/grep/ignore.py`、`agent/tools/grep/scan.py`、`test/tools/file_walk_test.py`、`test/tools/grep/ignore_test.py`
- 前置：[ADR 0006](0006-tool-permission-confirmation.md)（工具权限确认）、[ADR 0012](0012-tool-result-budget.md)（工具结果预算）

## 背景

两个发现工具回答的不是同一个问题：

- `glob` 回答“**这个文件在哪**”，答案要被 `read_file` 原样接受。目标可能是 `node_modules` 里的某份依赖实现，所以它不能隐藏任何名字。
- `grep` 回答“**这段代码写在哪**”，只该看仓库自己认定的源码。

第一版把这条区别只写进了文档，没写进行为，于是出现两个可测的问题：

1. `glob("**/*.js")` 在本仓库返回 100 条，其中 **82 条**是 `web-admin/node_modules/.vite/deps/*` 与 `web-admin/dist/assets/*`。原因不是它列出了依赖，而是“最新优先”把刚安装的 bundle 排到了最前面——列表还被截断了，于是整页都成了依赖。
2. `grep` 的跳过名单是手写的目录名（`node_modules`、`dist`、`build`…）。这是猜测：仓库自己已经在 `.gitignore` 里声明了“什么不是源码”，工具却没读。

此外 `grep` 还有一个自相矛盾的选项设想：给模型一个“是否过滤忽略文件”的开关。它会让同一份名单有两套行为、两套测试，而模型并没有判断“该不该”的依据。

## 决策

### D1. `glob` 不隐藏任何文件，只调整排序

排序键从 `(mtime desc, path)` 改为 `(是否生成物, mtime desc, path)`：项目源码在前，`SEARCH_SKIP_DIRS` 里的路径垫底。

“生成物”由 `is_generated_path()` 判定，只看**目录**段——一个名叫 `build` 的脚本仍是项目文件。

理由：`glob` 的承诺是“能找到任何文件”，这条不能动；而它的输出被截断到 100 条，顺序因此是契约的一部分。修好之后同一个查询是 **0 条**生成物。

### D2. `grep` 逐目录解析 `.gitignore`

进入某目录时读它的 `.gitignore`，规则按“祖先在前”拼接，**最后一条匹配生效**，因此 `!` 能撤销父目录的排除。支持 `#`、空行、`!`、`dir/`、`/anchored` 与全部通配语法；语义之所以能这么省，是因为 `GlobPattern` 的“无 `/` 即匹配任意深度的文件名”正是 git 的规则，新增的 `anchored=True` 专门表达 `/pattern`。

手写的 `SEARCH_SKIP_DIRS` **保留**，作为“仓库没写 `.gitignore`”时的地板（大量仓库从不提 `node_modules`）。

### D3. 忽略规则只从搜索根往下读，不读祖先

搜索根是模型的全世界：指哪搜哪。因此 `path="node_modules/react"` 仍然能搜到，即使工作空间根的 `.gitignore` 排除了 `node_modules/`。

这不是疏忽，而是唯一逃生口的实现方式：如果读祖先规则，指向被忽略目录也会被拒，模型就再无办法搜索它（除了 `exec_command`）。代价是 `path="web-admin"` 不会继承工作空间根的规则，与 git 的行为不同，这一点写在工具描述与术语表里。

同时接受 git 的既有语义：被忽略的目录不会下降，所以它下面的 `!` 无效。

### D4. 不给模型“忽略开关”

`.gitignore` 是仓库自己对“什么算源码”的声明；模型想越过它，就显式指 `path`。理由：

1. 开关意味着每个模式都有两套行为、两套测试，而收益只是省一次 `path`；
2. 模型没有判断依据——它不知道打开开关会让 20 秒预算被 `node_modules` 吃光；
3. 逃生口已经存在，且与 `glob` 的“显式 path 优先”是同一条规则。

二进制、超过 8MB、凭证类文件**不受**这条影响：它们是被内容检查排除的，不是被忽略规则排除的。

### D5. 忽略层必须便宜

忽略规则是每个遍历条目都要过的热路径。第一版对每条规则都算一次 `relative_to`，900 个文件的仓库要 1.2 秒；改为“只比文件名的规则不算相对路径、需要相对路径的按 base 缓存一次”后是 0.13 秒。

这条写进 ADR 而不是只写代码注释，是因为它是**约束**：以后新增任何规则语法，都要先在这条热路径上量一次。

## 后果

- `glob("**/*.js")` 这类查询重新变得可用；依赖仍然能被找到（只是排在后面），`path` 指进去仍能定向搜索。
- `grep` 现在遵守仓库自己的声明，`node_modules`、`dist`、`data/`、`*.min.js` 之类的自定义忽略都自动生效；`skipped_sensitive` 之外不再需要人肉维护名单。
- 两个工具的可见范围**不同**，而且这个不同是设计。文档（`docs/dev.md` §12）明确写了“不要为了一致性去改其中任何一个”。
- `path` 的语义在 `grep` 里多了一层含义：“指向被忽略的目录”既是逃生口，也是唯一能搜被忽略内容的方式。描述里必须写清，否则模型会以为搜不到就是没有。
- 忽略层的性能天花板由遍历条目数决定，与规则数近似线性；规则极多（数百条）的仓库会开始显现成本，目前没有索引优化，属于已知限制。

## 备选方案（未采用）

- **让 `glob` 也跳过 `SEARCH_SKIP_DIRS`**：会让 `glob` 找不到依赖里的文件，直接破坏“文件在哪”这个用途；而且用户的判断是对的——两个工具本来就不该有相同的可见范围。
- **只给 `grep` 加 `include_ignored` 开关**：见 D4。
- **只读根级 `.gitignore`**：省 70 行，但子项目自己的忽略规则会失效，而本仓库就有 `web-admin/` 这样的子项目。
- **`grep` 只靠硬编码目录名单**：名单永远滞后于仓库的真实布局，且无法表达 `*.min.js`、`data/` 这类项目自定义忽略。
- **解析祖先目录的 `.gitignore`**：与 D3 的逃生口冲突。
- **完整实现 git 的忽略方言**（`\#`/`\!` 转义、末尾空格、被忽略目录内的再包含）：语义成本高于收益，当前子集已覆盖实际仓库的写法。
