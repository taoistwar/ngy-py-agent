# ADR 0002: 文件工具的编码策略

- 状态：已接受（Accepted）
- 日期：2026-09-20
- 相关：`agent/tools/text_encoding.py`、`agent/tools/file_read_tool.py`、`agent/tools/file_edit_tool.py`
- 补充并部分取代：[ADR 0001](0001-file-edit-tool.md) 的 D4（"仅 UTF-8"）

## 背景

ADR 0001 的 D4 规定 `edit_file` 只接受严格 UTF-8，其他编码一律拒绝，理由是"编辑是破坏性操作，宁可拒绝"。但这造成一个不对称：`read_file` 用 `errors="replace"` 能把 GBK 文件"读"出来（内容里静默混入 `\ufffd`），同一个文件 `edit_file` 却直接拒绝——**读得到、改不了**，而且读到的还是被损坏的内容。

要判断能否放开，得先弄清一件事实：`edit_file` 当时的实现是"整文件解码 → 替换 → 整文件重编码"，这条路对非 UTF-8 是否会把**没被编辑碰过的字节**改掉。

## 事实

对"解码 → 重编码是否还原原字节"做了穷举扫描（2 字节空间 `0x81`-`0xFE` × `0x40`-`0xFE`，以及 GB18030 覆盖 U+0080–U+FFFF 的 4 字节带）：

| 编码 | 2 字节空间非双射序列 | BMP 4 字节带 | 整文件往返 |
| --- | --- | --- | --- |
| `utf-8` | 0 | — | 无损（且可证：唯一可解编码） |
| `gbk` | 0 | — | 无损（真实中文文本实测） |
| `gb18030` | 0 | 0 | 无损 |
| `shift_jis` | 0 | — | — |
| `big5` | **4** | — | 会改写未触碰字节 |
| `cp932` | **398** | — | 会改写未触碰字节 |

`cp932` 的实例：`b'\x87\x90'` 解码为 U+2252，重编码却是 `b'\x81\xe0'`。也就是**整文件重编码会改写编辑没有碰过的字节**。

结论：GBK 家族实测无损，所以"能正确修改 GBK 文件"是成立的；但"解码→编码无损"只是这两族编码的经验事实，不是普遍性质，所以写入方式本身必须改。

## 决策

### D1. 不静默猜测编码，失败时报错并给出候选，由模型显式重试

`read_file` / `edit_file` 都接受可选 `encoding`（默认 `utf-8`）。**BOM 优先**于该参数，因为那是文件自己的声明。解码失败时返回结构化错误，并在 `suggested_encodings` 里列出能解码这些字节的候选，由模型带 `encoding` 重试。

检测只用于生成提示，**不做自动回退**：猜错就是静默读错，与"宁可报错，不可读错"直接冲突。

候选分层：BOM（确定性）→ `charset-normalizer` 排序候选 → 候选编码试探（`gb18030`、`big5`、`shift_jis`、`euc-kr`、`cp1252`、`latin-1`）。`latin-1` 能解码任何字节序列，所以排在最后并标注"不构成证据"。任一层不可用时只是候选变短，不影响主流程（与 `agent/tools/tokenizers.py` 的可选导入风格一致）。

### D2. 放弃"仅 UTF-8"，支持任何可解码的编码

GBK 家族实测无损往返，可安全编辑；`cp932` / `big5` 的非双射问题由 D3 解决。

### D3. 写入改为字节级拼接，而不是整文件重编码

只在匹配到的**字节区间**上替换，其余字节原样搬运：

- 匹配仍解码后的文本上做（那是模型看到的东西，也是"严格匹配"的含义），
- 再由前缀编码长度换算字节偏移，并校验 `body[start:end] == old_string.encode(encoding)`，不通过就报 `encoding_mismatch` 拒绝写入，
- 写完后整体复核一次（重新解码必须等于预期文本），不通过同样拒绝。

这样 `cp932` / `big5` 也不会被改写未触碰的字节。

### D4. 不可编码的替换文本直接报错

`new_string` 在目标编码下编码失败时（例如 `😀` 无法用 GBK 表示）报 `unencodable_text`，**不做 `?` 替换**。

### D5. 新增依赖 `charset-normalizer`

只用于给候选排序，不用来替用户做决定。

## 后果

- `read_file` 会把 BOM 从正文里剥离，并在结果里以 `bom` 与 `encoding` 报告。此前 BOM 会作为 U+FEFF 留在正文第一行，导致读取文本与 `edit_file` 匹配用的文本不一致（BOM 文件的第一行永远匹配不上）。
- `reason="unsupported_encoding"` 被 `decode_failed` 取代，错误里多了 `suggested_encodings` 与 `encoding`。
- 编码相关逻辑集中在 `agent/tools/text_encoding.py`，读/写共用。
- 已知限制：非双射编码下，模型给出的 `old_string` 会编码成**规范字节形式**，可能与文件里实际存在的形式不同，此时结果是 `no_match`（安全失败），而不是误改。

## 备选方案（未采用）

- **用检测结果自动重读**：省一次往返，但猜错就是静默读错。
- **维持"仅 UTF-8"**：最安全，但把 GBK 文件变成只读，在中文项目里代价明显。
- **改用 `chardet`**：功能重叠，`charset-normalizer` 更活跃且已是 `requests` 的传递依赖。
