# ADR 0016: micro_compact —— 只缩短模型已经读过的结果

- 状态：已接受（Accepted）
- 日期：2026-10-26
- 相关：`agent/agent_loop/micro_compact.py`、`agent/agent_loop/loop.py`、`agent/agent_loop/result_budget.py`、`agent/tools/output_store.py`、`test/micro_compact_test.py`
- 前置：[ADR 0012](0012-tool-result-budget.md)（工具结果预算）、[ADR 0015](0015-snip-compact.md)（对话窗口裁剪）

## 背景

ADR 0012 与 ADR 0015 都作用在**结构**上，而且每步无条件执行：

| 步骤 | 触发 | 视角 | 代价 |
| --- | --- | --- | --- |
| `tool_result_budget` | 每步末，超过 200,000 字符 | 单批结果的字节 | 无损（内容落盘可读回） |
| `snip_compact` | 每步首，超过 50 条消息 | 消息条数 | 无损（历史落盘可读回） |

两者都不回答一个问题：**总量**。50 条消息、每轮都在预算内的结果，累加起来仍然可以是几十万字符；而其中大部分是模型**早就读过、也已经用过**的旧结果。它们仍在上下文里占位，只是因为没人有权把"已经发生过的事"删掉。

本 ADR 补上第三步：只在**估算出的上下文超过阈值**时，把这类旧结果换成一条可回读的路径。

## 决策

### D1. 只在超限时运行，且确定性、无模型调用

`micro_compact` 是压缩管线里唯一有条件的一步：

```
tool_result_budget（步末）→ snip_compact（步首）→ 超限？micro_compact → 仍超限？fit_tool_results → 仍超限只记账
```

前三步不动结构、不改顺序，只改写 `content`。第四步（LLM 摘要）需要一次模型调用、要处理"摘要失败"，而且摘要本身是不可核对的二次创作——本 ADR 明确不走这条路：`still_over` 只记一条事件，交给运维调阈值或调模型窗口。

> 更新（[ADR 0017](0017-compact-history.md)）：上面最后那句已被取代——`still_over` 为真时由 `loop.py` 调用 `compact_history`（归档 transcript → 摘要 → 一条 `[Compacted]` 标记）。本 ADR 其余结论（估算口径、阈值优先级、按 `tool_call_id` 判已读、复用确定性文件名、失败保留原文）不变。

### D2. 估算走结构化遍历，不用 `len(json.dumps(messages))`

参考实现的估算是一整表序列化。落到本仓库有两处不能接受：

- **图片**。截图以 base64 data URL 的形式存在于消息里（`agent.vision`），一张就是几 MB。按真实长度计，一个带截图的会话**永久**超限，而任何文本手术都救不回来——于是这一步每步都白跑一次落盘。
- **成本**。每次替换后重算 = O(n²) 次序列化 + 深拷贝语义。

实现为一次遍历求和（`estimate_chars`）：`content` 是字符串取长度；是 parts 列表时图片记 `IMAGE_CHAR_COST = 1,600`、文本取 `text` 长度；`tool_calls` 取 `arguments` 的字符串长度；每条消息加一个固定开销（角色、键、分隔符），否则一百条空 tool 消息会估算成 0。替换时用运行总量增减，全步只做两次全量估算（进、出）。

1,600 这个数不是精确的视觉计价：它是"够大，不至于把图片当免费；够小，不至于让截图本身成为超限原因"。真正精确的计费属于 provider，不属于压缩层。

### D3. 阈值：显式参数 > 环境变量 > 模型输入窗口 > 默认

`resolve_context_limit(configured, model_max_input_tokens)`：

1. 显式参数（测试与 API 用）；
2. `CONTEXT_CHAR_LIMIT`；
3. `max_input_tokens × 4`（`CHARS_PER_TOKEN`）；
4. `DEFAULT_CONTEXT_CHAR_LIMIT = 200,000`。

顺序里有两条判断：

- **模型窗口排在默认之前**：窗口是模型属性，已经在 `ProviderConfig.max_input_tokens` 里配过一次，不该让用户在两处各写一遍。
- **环境变量排在模型之前**：运维要能在不改模型记录的前提下临时收窄（复现一次超限、做一次压测）。这也是唯一能覆盖数据库配置的入口。

`<= 0` 关闭这一步。目标线是阈值的 80%（`TARGET_RATIO`），不是阈值本身：压到线上，下一步追加两条消息就又超了，然后每步都要压一次。

### D4. "已读"按 `tool_call_id` 判定，不按下标

`loop.py` 在每步请求发出**前**把当前所有 `role="tool"` 消息的 id 记进集合（`mark_seen`）。下一步开始时，这个集合就是"模型已经看过的东西"。

- **不能按下标**：`snip_compact` 会重写列表（`messages[:] = [...]`），之前记下的位置全部失效——而且失效是静默的，指向的是别的消息。
- **必须是每次 run 的局部状态**：`seen` 在 `run_react_loop` 内初始化，随 run 结束消失。放进模块级或 registry，并发任务会互相污染。
- **刚返回的结果在下一步仍属未读**：它们是在上一次请求之后才追加的，模型一眼都没看到。这正是"新结果保持完整直到模型读取一次"的字面实现。

### D5. 保留最近 3 条已读结果

`KEEP_RECENT_RESULTS = 3`。当前的活儿是建立在最近几条结果上的：刚读过的文件、刚跑完的命令。把它们换成路径，模型下一步就得为一个它正看着的内容再花一次工具调用。

更老的已读结果则可以换：它们要么已被消化进 assistant 的推理，要么可以按路径重新读回。

### D6. 复用已有落盘文件，文件名由 `tool_call_id` 决定

ADR 0012 已经规定文件名是 `<tool_call_id>.txt`。因此"这条结果是否已经落过盘"不需要 `content → path` 映射表：按 id 算路径、`exists()` 即复用。

- 第一步落过的结果，第三步直接复用，不产生第二份副本；
- 否则模型会看到两条路径指向同一份内容，还得自己猜哪个是权威；
- 只做 `exists()` 判定，不读回文件：读回是模型的动作，不是压缩层的。

命名规则与占位措辞都收在 `agent/tools/output_store.py`（`result_file_name` / `persisted_note`），第一步和第三步共用一套，避免出现两种"全文在这里"的说法。

### D7. `fit_tool_results` 的占位与 `micro_compact` 不同

两个步骤处理的是不同状态的结果，所以占位形状不同：

| | `micro_compact` | `fit_tool_results` |
| --- | --- | --- |
| 对象 | 已读、较老的结果 | **未读**的最新结果 |
| 占位 | `[Earlier tool result saved at <绝对路径>]`（单行） | `<persisted-output>`：路径 + 行数 + 1,000 字符预览 + 回读提示 |
| 理由 | 模型读过它，只需要知道去哪儿找 | 模型没读过，只给路径等于让它取一个形状未知的东西 |

`fit_tool_results` 只在"未读的最新结果自己就撑爆上下文"时介入：此时如果先去压旧历史，模型会在还没看到新结果之前就被要求放弃它们——忘错东西。

预览长度取 1,000 而不是第一步的 2,000：这一步的触发条件是"连它自己都放不下"，预览要小到能腾出空间。两个数字都来自同一个 `persisted_note`，只是参数不同。

### D8. 单条失败保留原文，继续下一条

落盘 `OSError` 时：该条**不替换**（全文留在上下文）、记入 `failed`、继续处理下一条，最后发一条 `error` 事件（最多列 10 条）。

不因为一条写不出就放弃整轮，也不静默丢掉内容——与第一步同一取舍：宁可超限（看得见），不可丢内容（看不见）。

### D9. 一轮一条 `debug` 事件

`prepare_context` 每轮只发一条汇总：阈值、目标线、前后字符数、micro/fit 各自替换条数、失败数、是否仍超限。逐步的明细没必要——操作员需要的分辨率是"这一步压了多少"。

已落盘的前缀（`<persisted-output>`）跳过，杜绝"指针指向指针"；短于 `MIN_SHRINK_CHARS = 120` 的结果也跳过，换成一个路径只会更长。

## 后果

- 上下文总量有了一个上界（阈值），而不再只是"条数上界 × 单条上界"。
- 被换掉的内容**全部可回读**：绝对路径 + `read_file`，受 ADR 0012 的回读契约约束（行号、单次 token 预算、256 KB 整读上限）。
- 压缩是**有损的提示面**：模型看到的不再是原文，而是一句"在哪儿"。它必须以一次工具调用换取内容——这是这一步的定价，也是保留最近 3 条的原因。
- 估算口径是字符而非 token：阈值与 `max_input_tokens × 4` 的换算对中文偏乐观（一个汉字可能 >1 token）。想要精确，就把 `CONTEXT_CHAR_LIMIT` 调低，而不是在压缩层里引入 tokenizer 依赖。
- 四家 provider 共用这一条消息层路径，没有适配器改动。
- `still_over` 不触发任何自动降级：需要模型摘要压缩时，那是新一步的设计，不是这一步的隐藏分支。

## 备选方案（未采用）

- **每步无条件压缩**：会破坏 prompt cache（每步都改写历史），且绝大多数步根本不需要。
- **删除旧结果而不落盘**：省一次 IO，代价是模型永远找不回被删内容。
- **按消息下标记"已读"**：`snip_compact` 重排后下标失效（D4）。
- **保留全部已读结果、只压缩未读**：真正的增长来自旧结果累积，只压未读等于没压。
- **未读结果也只给路径**：模型会为一个尚不知道形状的内容付一次盲读（D7）。
- **把 `still_over` 交给 LLM 摘要**：见 D1。
