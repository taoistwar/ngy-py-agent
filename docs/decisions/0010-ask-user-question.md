# ADR 0010: `ask_user_question` 工具与"提问通道"

- 状态：已接受（Accepted）
- 日期：2026-09-24
- 相关：`agent/tools/user_question.py`、`agent/tools/ask_user_question/`、`agent/tools/registry.py`、`agent/tools/bindings.py`、`agent/agent_loop.py`、`main.py`、`web-admin/src/components/QuestionPrompt.jsx`
- 前置：[ADR 0005](0005-exec-tool.md)、[ADR 0006](0006-tool-permission-confirmation.md)、[ADR 0008](0008-write-stdin-tool.md)

## 背景

参考实现（Codex）有一个 `request_user_input`：模型提交 1–3 个问题、每题 2–3 个互斥选项，客户端渲染成对话框，答案以 `{"answers": {"<id>": {"answers": [...]}}}` 的形式回到模型。它的几个关键做法在本仓库要么不成立、要么不该照抄：

| 参考实现 | 本仓库的现状 |
| --- | --- |
| schema 里只有描述性约束（无 `maxItems`/`maxLength`，`strict: false`） | 可以照抄：数字写进描述，机器只强制结构 |
| 永久阻塞（`rx_response.await`，无超时） | **不能照抄**：本仓库有"无人值守的 Web 服务"和"CLI 没有客户端"两种现实场景，永久阻塞等于把任务挂死 |
| 无人应答时非交互客户端回填空答案 | 同向，但本仓库要把"为什么是空的"讲清楚 |
| 自由文本用客户端私有编码 `user_note: <text>` 塞进同一个数组 | **不该照抄**：把客户端编码混进模型可见的数据契约，用户真选了名字叫 `user_note: xxx` 的选项就会读错 |
| Plan 模式才有；仅 root thread；feature + 配置双重开关 | 本仓库的 `plan` 模式**一个工具都没有**（`agent/modes.py`），照抄正好是反的 |

最关键的一条是本仓库的既有事实：**工具拿不到 `EventSink`，也拿不到 `PermissionBroker`**（`ToolBindings` 里没有它们，术语表把这条钉死了）。今天唯一"工具 → 人 → 工具"的通路是权限门禁，而那条通路**只能回传布尔**：`check()` 返回 `None` 或 `PermissionDenial`，用户在对话框里填的任何文本都到不了工具手里。所以"提问"不是加一个工具那么简单，它需要一条**新的入站通道**。

同时，等待本身不需要新机制：`TaskStatus.WAITING` 的语义（"仍属 in flight，推流不能断"）、`_sink` 的状态机、前端 1 秒轮询 `pending_*` 渲染对话框，这些在 ADR 0006 / 0008 里已经建好了。

## 决策

### D1. 独立的 `UserQuestionBroker`，与权限代理正交

提问与权限是两条**正交的轴**：P 轴问"能不能做"（无应答即拒绝，fail closed），Q 轴问"该做什么"（无应答不等于禁止继续）。两者的事件类别、答复体、超时语义、审计含义都不同，所以不复用 `PermissionBroker`，而是新建 `agent/tools/user_question.py`，只借它的骨架：任务线程阻塞在 broker 里，另一个线程（API）通过 `resolve()` 交付答复，等待用 0.25 秒轮询而不是硬阻塞，停止信号优先于超时。

工具**不自己拿 broker**：通道以 `ToolBindings.ask_user`（一个可调用对象）注入，由 `ToolRegistry.ask_user` 在**每次调用时**读取 `self.user_question_broker`。这与 ADR 0006 D1 的晚绑定是同一个手法（registry 建得比任务身份早），也让工具保持"没有 task_id、没有 sink"的既有不变量。

### D2. 无人应答不是拒绝：超时 = 空答案 + 一句"自行决定"

- 超时（`ASK_USER_TIMEOUT_SECONDS`，默认 120 秒）、任务被停止、没有客户端，三者都返回**空答案集**，并附一句模型可见的说明：没有答案、请基于现有信息自行决定并说明假设、不要再问一遍。
- **不 fail closed**。权限的"没人回答 = 不行"是对的，因为沉默不能当允许；提问的"没人回答 = 不行"是错的，它会把"用户不在"变成"模型必须停下来"，而它完全可以带着假设继续。
- **不永久阻塞**（参考实现的做法）。本仓库的 Web 服务可以在无人连接时跑任务，CLI 根本没有客户端；永久阻塞在这些场景里只会等到任务被停止。
- 超时用**自己的环境变量**，不复用 `PERMISSION_TIMEOUT_SECONDS`：两者读起来一样，含义不同（"拒绝这次调用" vs "带着假设继续"），共用一个旋钮会让调整一个时误伤另一个。
- 停止优先于超时（与 ADR 0006 D6 同一条规则）。

### D3. 两个新事件类别，工具本身不发第三个

`user_question`（携带问题原文，`is_other: true`）与 `user_answer`（携带 `status`、`answers`、`answered_count`），由 broker 发出，`_sink` 复用既有状态机：前者 `WAITING`、后者 `RUNNING`。工具返回普通的 `ToolOutcome`（无 `event_category`）——`tool_result` 已经记录了这次调用，再发一个同载荷的事件只会多一处可能不同步的地方。

状态机的判定被抽成 `app_state.status_for_event`，因为它现在服务两条通道，藏在 `_sink` 的闭包里没法测。

### D4. 没有客户端时如实说"没人可问"

`ask_user` 未绑定（库调用、CLI、测试）时返回 `status = "no_client"` 的不阻塞结果，模型拿到空答案 + 说明。**不抛异常、不阻塞、也不假装问了**。

交互式 REPL 里"真的在终端问用户"记为后续子项目：它要与 REPL 的输入循环互斥（模型跑的时候终端也在读 stdin），还要处理并发任务与等待期间的 Ctrl+C，是独立一轮的工作量。

### D5. 答案形状：数组、不加前缀、自由文本是独立元素

```json
{"answers": {"approach": {"answers": ["Patch it", "只在 parser 里改"]}}}
```

- 选项标签自己占一个元素，用户输入的自由文本**另占一个元素**，顺序即"选择、补充"。**不采用**参考实现的 `user_note: ` 前缀：那是客户端私有的编码方式，混进模型可见契约后，模型只能靠字符串前缀猜这一条是用户原话还是选项，而且用户真选了同名选项就会读错。
- 客户端加的"其他"行不产生任何标签，只把用户输入作为答案；`details` 里另给一份结构化副本供 UI 与审计使用。
- 每题最多一个选项 + 可选一段自由文本（选项互斥），数组长度天然 ≤ 2。

### D6. 权限与可用范围

- `permission = none`：提问不是特权动作，在它前面再挂一个"允许提问吗"的确认框，正是工具描述明令禁止的那种混淆。工具描述里写明"不要用它请求权限"（与参考实现一致）。
- 可用范围：`build`（`tool_names = None`，自动包含）与 `ask`（显式加入，因为"含糊就先问清楚"正是该模式的指令）；`plan` 保持无工具——它的契约是产出计划，不是发问。
- 它不改变任何东西（只读 + 阻塞），因此没有需要声明的能力种类。

### D7. 数字是描述，结构才是强制

- 只写进描述：1–3 题、优先 1 题、每题 2–3 个互斥选项、`header` ≤ 12 字符、推荐项放第一并加 "(Recommended)"。schema 里**不设** `maxItems`/`maxLength`（与参考实现一致）。
- 机器强制（`questions.py`）：`questions` 非空数组、每题有非空 `id` 与 `question`、每题至少一个选项、每个选项有非空 `label`、**id 唯一**（答复是以 id 为键的字典，重复 id 会让答案静默错位，因此这是契约正确性问题，不是风格问题，与上面那条不冲突）。`header` 允许缺失，缺失时用问题文本前 40 字符兜底。
- 选项的 `description` 可选：模型可见的 schema 只把 `label` 列为必需，因为对话框没有描述也能渲染；描述里仍要求写一句取舍。（这是与参考实现的一处小偏离，记在这里。）

### D8. API：新端点 + 任务详情里的 `pending_question`

- `POST /api/tasks/{task_id}/question/{request_id}`，请求体 `{"answers": {...}}`。
- 校验**拒绝而非降级**：未知任务 404；请求不是当前 pending 的那个 409；未知问题 id、非字符串答案 400（`validate_answers` 在 broker 模块里，与工具共享同一份形状知识）；重复答复 409。
- `pending_question` 加进 `GET /api/tasks/{id}` 与任务列表，与 `pending_permission` 并列：前端轮询它渲染对话框，断线重连的客户端也能看到待答的问题。

### D9. 前端是纯表单

每题一组单选按钮 + 一个自由输入行 + "提交/跳过"两个按钮；不抄参考实现的键盘 overlay（列表选择、Tab 进备注、自动解析倒计时）。**跳过 = 空答案集**：它比让用户等满超时更诚实，也让"不要等我"有一键的出口。对话框不可用 Escape 静默关闭（静默结局只会是超时），Escape 与关闭按钮都走"跳过"。

## 后果

- 模型多了一条**只读且阻塞**的能力：把一次含糊的决策交回用户，而不是猜一个然后返工。
- 审计上两条通道互不冒充：`permission_request/decision` 是"允许/拒绝"，`user_question/user_answer` 是"问了什么/答了什么"。
- 已知限制（明写）：
  - CLI 与库调用没有客户端，只会拿到 `no_client`；
  - 超时后模型继续用假设推进（描述里要求它说明假设）；
  - 单选，不支持一题多选；
  - 前端不做键盘快捷键、不做倒计时自动提交（本仓库的对话框只有提交/跳过两个出口）。
- 新增一套阻塞等待代码（与权限代理形状相同、语义不同）。这是有意的重复：把两者合成一个"什么都代理"的类，会让两条轴的语义在一个地方互相污染。

## 备选方案（未采用）

- **复用 `PermissionBroker`**：混淆 P 轴与 Q 轴，且它只能回传布尔，硬扩展会把两个答复体塞进一个事件。
- **两阶段 `ToolOutcome`**（工具返回"我要提问"，`agent_loop` 提问后再调用一次工具）：把一次逻辑调用拆成两次模型可见的调用，模型要理解"同一问题的两半"，而收益只是不必新增 broker。
- **照抄永久阻塞**：无人值守的部署里等于挂死任务。
- **无人应答 = 拒绝**（fail closed）：把"用户不在"谎报成"禁止继续"。
- **照抄 `user_note: ` 前缀**：客户端编码混进模型可见契约，见 D5。
- **复用 `permission_*` 事件类别**：时间线上无法区分"允许了命令"与"选了方案"。
- **按能力裁剪工具清单**（无客户端时不暴露这个工具）：需要新增"按运行环境裁剪 schema"的机制（本仓库的清单是静态的），而 `no_client` 的结果已经够诚实。
- **前端抄 overlay / 支持多选**：本仓库的对话框是简单表单，键盘交互与多选都要各自的测试与快照，收益低于成本。
